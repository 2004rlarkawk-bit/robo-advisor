[2] AI 로보어드바이저 정의 (3가지 구현 방식)
────────────────────────────────────────────────────────────────

방식 A — LLM 단독
- GPT-4/Claude API 호출만
- 장점: 구현 빠름
- 단점: 환각, 통관 규정 틀려도 그럴듯, API 비용

방식 B — RAG (Retrieval-Augmented Generation)
- 법령·HS코드·과거 문서 벡터DB → 검색 → LLM에 컨텍스트 주입
- 장점: 최신·정확, 환각 줄임, 출처 제시
- 단점: 벡터DB 구축, 검색 품질 의존

방식 C — Rule + ML 하이브리드
- HS분류·필수항목 검증 = 룰엔진
- 자연어 설명·요약 = LLM
- 장점: 규정 위반 0, 검증 가능, 안정적
- 단점: 룰 작성 노가다, 규정 변경 시 수동 업데이트

★ 본인 추천: RAG + 부분 룰엔진
이유: 통관 = 정확성 필수, 환각 = 관세법 위반 리스크

[4] 데이터 확보 — 3개 소스 → AI 능력 3개 매핑
────────────────────────────────────────────────────────────────

AI에게 필요한 3가지 능력:
능력 1 — 문서 형식 알기 (Invoice·Packing List·신고서 양식)
능력 2 — 품목 → HS코드 분류
능력 3 — 규정 위반 검출 (법령·규제·허가)

★ 데이터 소스 → 능력 매핑 매트릭스
(◎ 메인 / ○ 보강 / △ 부분 / ✗ 없음)

소스 1) UNI-PASS Open API (HS코드·관세율·환율)
- ① 문서형식: ✗
- ② HS분류: ◎ (메인 — 코드 1만개 + 한글·영문품명 + 관세율)
- ③ 규정검출: △ (관세율 ≠ 0 → 신고 의무)

소스 2) 관세청 공공데이터 (법령·고시·통계)
- ① 문서형식: ✗
- ② HS분류: △ (코드 정의 있지만 학습엔 부족)
- ③ 규정검출: ◎ (메인 — RAG 지식베이스 핵심, 출처 인용 가능)

소스 3) 멘토 네트워크 — 익명화 실문서 5~10건
- ① 문서형식: ◎ (메인 — 유일한 소스)
- ② HS분류: ○ (실제 품목 표기 학습)
- ③ 규정검출: ○ (반려 사례 = 흔한 오류 패턴)

★ 결론: 3개 모두 필요. 1·2번 = 즉시 가능. 3번 = 멘토 협조 필수, 없으면 데모 수준에서 멈춤.

[6] 경쟁 4사 분석 정리
────────────────────────────────────────────────────────────────

1) Maersk Trade & Tariff Studio
- 글로벌 1위 선사 (덴마크) AI 통관 SaaS
- 2025.6 출시
- 성격: 분류·검증·관세 절감 (분석가)
- 문서 생성 X
- 타깃: 대기업·다국적 화주
- 가격: 비공개 B2B 엔터프라이즈
- 강점: HS 6,000+ / 서브 20,000+, 전문가 2,700명 네트워크
- 사용 시점: 출하 결정 후, 신고 전 (사전 리스크 분석)

2) Digicust (오스트리아·독일)
- AI 통관 신고서 자동 작성 (가장 가까운 경쟁자)
- 70~90% 자동화율, 추출 정확도 98%
- 단 "기존 문서 업로드 → 추출·재구성" 방식
- 무에서 유 X
- 한국어 X, 유럽 규정 특화

3) UNI-PASS (한국 관세청)
- 공식 전자통관 인프라 (필수 사용)
- 수출입 신고서 제출·처리·세금 납부·조회
- AI X, 양식 작성은 사용자 몫
- 무료, 모바일 앱 + Open API 제공
- UI 업무용 — 무역 초보엔 어려움

4) 국내 RPA (관세법인)
- 엑셀 → UNI-PASS 입력 자동화
- 인보이스 OCR 추출, 관세 비용 계산, 신고 결과 조회
- 정형·반복만, 비정형·판단 X
- "5시간 → 5분" 사례

★ 차별점 (우리 자리)
- "문서 생성 + 필요 서류 판단" 동시 = 어디에도 없음
- 한국 중소기업·신규 무역 담당자용 advisory = 비어있음
- AI Agent 생성-검토-피드백 통합 흐름
- 모바일 보완 안내 = 미개척

★ 포지셔닝 한 줄
"한국 중소 무역기업용, LLM Agent 기반 통관 문서 작성 + 필요 서류 추천 + 누락 자동 검토 + 모바일 보완 안내 통합 서비스"

★ Maersk vs 우리 (발표용)
- Maersk = "얼마 물고 어디 막힐지 알려줌" (분석가)
- 우리 = "뭐 써야 할지 + 직접 써줌 + 검토까지" (어드바이저+작성자)

★ 관세사는 왜 안 쓰나
- 본인이 이미 어드바이저
- 책임 문제 (AI 결과 그대로 신고 후 오류 시 본인 책임)
- 기존 사내 시스템·RPA 충분
- 가격 무료여도 신뢰 검증 시간 ↑
→ 페르소나 X. 중소기업 1순위.


[7] HS코드 분류 방식 (정확도 순위)
────────────────────────────────────────────────────────────────

1위 — 계층 분류 + RAG + LLM 하이브리드 (SOTA)
- 정확도: 6자리 85~95%, 10자리 70~85%
- 구조: Chapter(99) → Heading(1.2K) → Subheading(5.4K) → HSK(10K+) 단계별 모델
- 단계별 모델 N개 (BERT/RoBERTa 파인튜닝)
- 단점: 데이터·GPU·관리 부담 N배, 오류 전파

2위 — 파인튜닝 BERT 단일 분류
- 6자리 80~90%
- 데이터 10만건+ 필요

3위 — 임베딩 유사도 + LLM 재랭킹 ★ 너희 추천
- 6자리 75~85%
- 학습 0, 즉시 구현
- Sentence-BERT / OpenAI embedding + Top-K + LLM 선택

4위 — 임베딩 단독: 6자리 60~75%
5위 — LLM zero-shot: 6자리 50~70%, 환각 큼
6위 — API 단순 키워드: 40~60%

★ 5개월 권장 = 3위 방식 + 룰엔진. 75~85% 목표.
★ 발표 포지셔닝: "SOTA는 계층 하이브리드지만 일정 고려해 임베딩+LLM 조합. 미달분은 사용자 선택 UI로 보완."
→ 학술적 정직성 어필

[9] DB·코드·UX·UI·프론트엔드 개념 정리
────────────────────────────────────────────────────────────────

DB ≠ 코드. DB = 데이터 저장소.
- 비유: 인터넷 서버에 있는 거대한 엑셀
- 코드(Python/JS)가 DB에서 데이터 읽고·씀

Supabase = DB + 인증 + 파일저장 + 실시간 묶어 빌려주는 클라우드
- 사이트(supabase.com) 로그인 = 개발자용 대시보드
- 연결 문자열 1줄 = 코드↔DB 통신
- 우리 앱 사용자 로그인은 또 별개

UX vs UI vs 프론트엔드
- UX = 흐름·논리 설계 (와이어프레임, Figma)
- UI = 시각 디자인 (색·폰트·컴포넌트)
- 프론트엔드 = 실제 코드 구현 (React 등)
- 학부 팀: 한 사람이 셋 다 (모자 3개 번갈아)
- 작업 순서: UX → UI → 코드


[10] 페르소나별 요구사항 차이
────────────────────────────────────────────────────────────────

A) 중소 수출기업 신규 담당자 ★ 우리 1순위
- UI: 단계별 위저드, 용어 풀이, 그림 가이드
- 입력: 최소 (품명·수량·국가) → 나머지 AI
- AI 역할: 어드바이저 강함 (왜 필요한지 설명)
- 결과물: 즉시 제출 가능 문서 + 체크리스트
- 모바일: 필수
- HS코드: 자동 추천 + 사용자 확인

B) 관세사
- UI: 정보밀도 ↑, 키보드 단축키, 일괄 처리
- 입력: CSV·엑셀 대량
- AI 역할: 작성자 + 검증자
- 신뢰: 근거·출처 필수
- 모바일: 우선순위 ↓

C) 포워더
- UI: 화물별 대시보드, 캘린더
- AI 역할: 일정·서류 조율 (다수 화물 병렬)
- 연동: UNI-PASS·ERP 통합
- 모바일: 푸시 알림 강함

★ 결정: 중소기업 1순위
근거:
- 경쟁 4사 모두 중소기업 X (Gap)
- 5개월 학부생 = MVP 좁히기
- 어드바이저 컨셉 = 중소기업에 최대 가치
- 조장 도메인 강점 활용 가능


[11] 팀 4명 역할 분담 (바이브 코딩 시대)
────────────────────────────────────────────────────────────────
