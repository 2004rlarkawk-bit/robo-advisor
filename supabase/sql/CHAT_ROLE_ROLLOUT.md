# 통합 계정 기존 채팅 적용

이 변경은 별도 대화방이나 로컬 저장을 만들지 않습니다.
기존 trade_messages에 발신 역할을 저장하고 양쪽 화면에서 상대 역할의 메시지를 읽습니다.

## 함께 적용할 코드

- tradeMessageService: sender_role 전송, 역할별 읽음 및 미확인 수
- TradeMessageThread 및 화주/포워더 호출부: 현재 작업 역할 전달
- notificationService: recipient_role로 알림 분리
- tradeMessageGrouping: 같은 계정이라도 역할이 다르면 다른 발신자로 표시
- migrations/20260923090000_trade_message_sender_role.sql

## 적용 순서

1. 위 프론트 코드가 포함된 커밋의 테스트·빌드를 확인합니다.
2. DB에서 sender_role 유무 및 기존 함수/정책을 확인하고 백업합니다.
3. 사용자가 채팅하지 않는 배포 시간에 SQL을 적용합니다.
4. 바로 같은 커밋의 웹을 배포하고 브라우저를 새로고침합니다.
   기존 웹은 본인 의뢰 메시지에 역할을 보내지 못하므로 DB만 적용하고 두지 않습니다.
5. 통합 계정의 같은 의뢰에서 화주 메시지 전송 → 포워더로 전환 →
   수신·읽음 확인 → 답장 → 화주로 전환 후 수신·알림을 확인합니다.
6. 서로 다른 계정의 정상 대화, 제3자의 접근 거부, 종료 의뢰 전송 거부도 확인합니다.

## 주의

- SQL은 재실행 시 기존 역할이 있는 메시지를 덮어쓰지 않습니다.
- 과거 본인 의뢰 메시지는 발신 역할을 추측하지 않아 null로 남습니다.
- 읽음 이외의 메시지 변경 금지는 의도한 보호입니다. 관리자 백필은
  별도 검토한 마이그레이션에서 트리거를 관리해야 합니다.
- 현재 작성 환경에서는 운영 DB 적용/실제 로그인 왕복 테스트를 실행하지 않았습니다.
- 이전 버전으로 웹만 되돌리면 본인 의뢰 전송은 다시 실패합니다.
  문제 발생 시 채팅 사용을 중단하고 DB/웹 버전을 함께 점검합니다.
